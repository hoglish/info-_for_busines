# DECISIONS.md

## Индивидуальный вариант №26

### Часть А (корректировка существующего метода):
Метод `parseHours(String line)` изменён для приёма 6 значений вместо 5. Шестое значение представляет собой почасовую ставку (double). Метод проверяет формат ставки через `Double.parseDouble()`, но возвращает массив только из первых 5 целочисленных значений (часы за рабочие дни). Это позволяет расширить функционал без изменения возвращаемого типа базового метода `int[]`.

### Часть Б (новый метод):
Добавлен метод `addPayForWeek(int[] hours, double rate) → double`. Он рассчитывает полную оплату за неделю по формуле: `(totalHours × rate) + (weeklyOvertime × rate × 1.5)`. Это реализует бизнес-логику расчёта зарплаты с учётом полуторной оплаты за сверхурочные часы. Метод использует существующие методы `total()` и `weeklyOvertime()` для соблюдения принципа DRY.

## Решение 1: Валидация ставки в parseHours

**Формулировка:** При разборе строки табеля необходимо проверять не только часы, но и ставку оплаты.

**Альтернатива:** Можно было создать отдельный метод `parseRate(String line)`, который бы извлекал ставку из строки.

**Обоснование:** Выбор в пользу расширения `parseHours` обусловлен тем, что ставка является частью входных данных и должна валидироваться одновременно с часами. Это сохраняет стратегию fail-fast: если ставка некорректна, программа сразу сообщает об ошибке, не пытаясь обработать "битые" данные. Кроме того, это минимизирует количество методов и упрощает структуру класса.

## Решение 2: Вычисление оплаты через существующие методы

**Формулировка:** Метод `addPayForWeek` делегирует вычисление суммы часов и переработки методам `total()` и `weeklyOvertime()`.

**Альтернатива:** Можно было бы реализовать всю логику суммирования внутри `addPayForWeek` напрямую, без вызова вспомогательных методов.

**Обоснование:** Использование существующих методов соответствует принципу DRY (Don't Repeat Yourself). Если в будущем изменится формула расчёта суммы часов или недельной переработки, достаточно будет поправить только один метод, и все зависимые методы автоматически получат актуальную логику. Это также упрощает тестирование: каждый метод проверяется независимо.

## Ответы на контрольные вопросы

### Вопрос 1: Какая проверка защищает программу от наиболее вероятной ошибки входных данных?

Наиболее вероятной ошибкой входных данных является нарушение структуры строки — пользователь может ввести меньше или больше 5 значений, забыть разделитель или добавить лишний. Проверка количества значений после `split(";", -1)` расположена в методе `parseHours()` класса `TimesheetAnalyzer` в самом начале обработки. Она защищает программу, потому что без корректного количества элементов невозможно однозначно сопоставить значения дням недели. Если бы эта проверка отсутствовала, программа могла бы выбросить `ArrayIndexOutOfBoundsException` при обращении к несуществующему элементу массива, что привело бы к непредсказуемому поведению.

### Вопрос 2: Какой метод содержит ключевое бизнес-правило и почему он размещён именно там?

Ключевое бизнес-правило — формула расчёта недельной переработки `max(0, sum − 40)` — содержится в методе `weeklyOvertime(int[] hours)` класса `TimesheetAnalyzer`. Этот метод размещён именно здесь, потому что он является чистой функцией: не имеет состояния, зависит только от входных параметров и легко тестируется. Размещение бизнес-логики в статическом методе утилитарного класса позволяет переиспользовать её в разных контекстах (расчёт оплаты, формирование отчётов, анализ нагрузки) без создания экземпляров объекта.

### Вопрос 3: Как Activity-диаграмма отражает один конкретный участок кода?

Блок TODO A1 на Activity-диаграмме с формулировкой "Для каждого элемента: проверить regex и диапазон [0, 16], преобразовать в int" соответствует циклу `for (int i = 0; i < 5; i++)` в методе `parseHours()`. Внутри цикла выполняются три проверки: соответствие регулярному выражению `^(0|[1-9][0-9]*)$`, преобразование через `Integer.parseInt()` и проверка диапазона `0 ≤ v ≤ 16`. При нарушении любого условия цикл прерывается выбросом `IllegalArgumentException` — это отражено на диаграмме ветвлением "Все элементы корректны?" с переходом к блоку формирования ошибки.

### Вопрос 4: Какое изменение требования должно затронуть минимальное количество классов?

Изменение порога дневной переработки с 8 на 9 часов затронет только один метод — `overtimeDays()` в классе `TimesheetAnalyzer`. Если порог вынесен в именованную константу `DAILY_NORMAL_HOURS`, изменение потребует правки только одной строки кода. Это возможно благодаря декомпозиции: каждый метод отвечает за одну задачу, и бизнес-правила локализованы. Если бы вся логика была в одном большом методе, изменение порога потребовало бы анализа всего кода и могло бы привести к случайным ошибкам в других частях.

## Фрагмент кода для анализа

Рассмотрим фрагмент с ошибкой off-by-one:
```java
for (int i = 0; i <= hours.length; i++) {
    total += hours[i];
}
```

Техническая ошибка: условие i <= hours.length приводит к выходу за границы массива на последней итерации, когда i равен hours.length. Причина: путаница между индексом последнего элемента (length - 1) и длиной массива. Исправленное условие: i < hours.length. Эта ошибка нарушает правило R1, так как при обработке строки с ровно 5 значениями программа попытается обратиться к 6-му элементу и завершится с ArrayIndexOutOfBoundsException вместо корректного расчёта.
