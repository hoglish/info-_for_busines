# DECISIONS.md – Практическая работа 10

## Вариант

Номер варианта: 26

**Часть А.** Добавлен тип доставки `LOCKER` (постамат): значение в `DeliveryType`,
класс `LockerPolicy implements DeliveryPolicy` и новая ветка `case LOCKER` в `DeliveryPolicyFactory.get`.
`LockerPolicy.supports` принимает любой запрос (как `PickupPolicy`), `calculateCost` всегда возвращает 200 руб.
Фиксированная стоимость задана одной константой `LockerPolicy.FIXED_COST`.
Существующие политики (`StandardCourierPolicy`, `ExpressPolicy`, `PickupPolicy`) и метод
`DeliveryService.calculate` не менялись — это демонстрация Open/Closed Principle (R9).

**Часть Б.** `DeliveryService.addLockerCost(DeliveryRequest)` — стоимость доставки типа LOCKER
для параметров запроса. Тип запроса подменяется на LOCKER, остальные поля копируются, далее вызывается
обычный `calculate`, то есть тот же полиморфный путь. Для совместимости с формой из задания
`addLockerCost(DeliveryService, DeliveryRequest)` добавлена статическая перегрузка.

## Решение 1. Фабрика через switch expression без default

Формулировка: `DeliveryPolicyFactory.get` — единственное место выбора реализации; `switch` по enum
без ветки `default` и без `null`.

Альтернатива: `Map<DeliveryType, DeliveryPolicy>` или `if-else` в `DeliveryService`.

Обоснование: `switch` по enum проверяется компилятором на полноту. Если добавить значение в
`DeliveryType` и забыть про фабрику, код не скомпилируется — ошибка видна сразу, а не в рантайме.
`if-else` в сервисе нарушил бы R8 и OCP.

## Решение 2. Валидация в компактном конструкторе record DeliveryRequest

Формулировка: отрицательные расстояние, вес, сумма заказа и `type == null` отсекаются в момент создания
запроса (`IllegalArgumentException`).

Альтернатива: проверять данные в каждой политике или в `DeliveryService.calculate`.

Обоснование: запрос иммутабелен, поэтому один раз проверенный объект безопасен для всех политик.
Проверки не размножаются по классам. Вес 0 допустим сознательно: открытый sample.csv содержит строку
с нулевым весом, ожидающую корректный расчёт.

## Ответы на контрольные вопросы

### Вопрос 1
Наибольшую гибкость даёт Open/Closed Principle, реализованный парой Strategy + Factory. Интерфейс
`DeliveryPolicy` задаёт единый контракт, каждая политика (`StandardCourierPolicy`, `ExpressPolicy`,
`PickupPolicy`, `LockerPolicy`) инкапсулирует свою формулу, а `DeliveryPolicyFactory` выбирает реализацию по типу.
`DeliveryService` работает только с интерфейсом и вызывает `policy.calculateCost(req)` полиморфно. Поэтому
четвёртый тип доставки (в моём варианте LOCKER) добавляется тремя шагами: значение enum, новый класс и
новая ветка `case` в фабрике. Существующие политики и сервис при этом не правятся, риск регрессии
остальных способов доставки минимален.

### Вопрос 2
Ключевая логика выбора стратегии находится в классе `DeliveryPolicyFactory`, метод `get`. Это правило R4:
фабрика отвечает только за выбор реализации и не содержит формул расчёта. Я разместил выбор именно здесь,
чтобы при добавлении нового типа доставки изменение локализовалось в одном классе: появляется новая ветка
`case`, а сервис и другие политики остаются нетронутыми. Это соответствует Single Responsibility Principle:
фабрика знает, какой класс создать; политика знает, как считать; сервис знает, в каком порядке вызывать
выбор, проверку `supports` и расчёт. Формулы в фабрике сделали бы её вторым местом, которое надо править
при смене тарифа.

### Вопрос 3
Блок «A1: Получить политику доставки через Factory по типу запроса» на Activity-диаграмме соответствует
строке `DeliveryPolicy p = factory.get(r.type());` в методе `DeliveryService.calculate`. Следующий блок
«Проверить возможность доставки (policy.supports(req))» — это вызов `p.supports(r)`, ромб «Доставка возможна?»
— условие `if (!p.supports(r))`, ветка «нет» — `throw new IllegalArgumentException("Unsupported delivery")`,
ветка «да» — `return p.calculateCost(r)`. Дополнительный блок части Б соответствует методу `addLockerCost`,
который подставляет тип LOCKER и затем идёт тем же путём. Каждому вызову в коде соответствует узел диаграммы,
и наоборот.

### Вопрос 4
Минимальное число классов затрагивает смена лимита веса стандартной доставки, например с 20 на 15 кг:
меняется только `StandardCourierPolicy`, а точнее одна константа `MAX_WEIGHT_KG`. Формула и проверка
инкапсулированы в классе-политике, фабрика, сервис, остальные политики и диаграммы не меняются. Меняются
лишь ожидания в тестах и строках sample.csv, где вес попадает между старым и новым лимитом. То же верно для
стоимости постамата: она задана константой `LockerPolicy.FIXED_COST`. Благодаря интерфейсу `DeliveryPolicy`
зависимость сервиса от конкретных тарифов отсутствует, поэтому изменение формулы не распространяется дальше.

## Фрагмент кода для анализа

Фрагмент:

```java
if (type == EXPRESS) { ... } else if (type == STANDARD) { ... } else if (type == PICKUP) { ... }
```

Проблема: один метод хранит все алгоритмы расчёта и знает обо всех типах доставки, что нарушает
Single Responsibility Principle и Open/Closed Principle. Добавление нового типа (например, LOCKER) требует
правки этого метода — новой ветки `else if`, причём любая ошибка рискует сломать существующие ветки.
Это нарушает R2 (расчёт не должен зависеть от названий способа после выбора стратегии) и R8
(`DeliveryService.calculate` не должен содержать `if-else` по типам).

Исправление: интерфейс `DeliveryPolicy` + классы-реализации + `DeliveryPolicyFactory` для выбора;
расчёт выполняется полиморфным вызовом `policy.calculateCost(req)`:

```java
DeliveryPolicy policy = factory.get(req.type());
if (!policy.supports(req)) throw new IllegalArgumentException("Unsupported delivery");
return policy.calculateCost(req);
```
