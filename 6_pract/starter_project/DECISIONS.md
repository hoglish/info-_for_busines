# DECISIONS.md

## Индивидуальный вариант №26

### Часть А (корректировка правила):
В метод `route()` добавлена проверка запрета комбинации `urgent == true` и `containsPersonalData == true`. Эта проверка имеет высший приоритет (выше R1). При нарушении выбрасывается `IllegalArgumentException("Urgent personal data is not allowed")`. Обоснование: срочные заявки с персональными данными требуют ручного согласования и не могут обрабатываться автоматически, даже службой безопасности.

### Часть Б (новый метод):
Добавлен метод `addUrgentPersonalCheck(boolean urgent, boolean containsPersonalData) → boolean`. Возвращает `true`, если комбинация параметров допустима для автоматической маршрутизации, и `false`, если она запрещена. Метод используется для предварительной валидации перед вызовом `route()`, позволяя caller'у избежать обработки исключения.

## Решение 1: Приоритет запрета над правилом R1

**Формулировка:** Проверка запрета `urgent && personal` размещена перед проверкой R1 (`containsPersonalData`).

**Альтернатива:** Можно было бы реализовать запрет внутри блока R1 или создать отдельный маршрут `MANUAL_REVIEW`.

**Обоснование:** Размещение проверки до R1 соответствует стратегии fail-fast. Запрет является инвариантом системы, который не зависит от бизнес-правил маршрутизации. Выброс исключения сразу предотвращает попытку маршрутизации недопустимой заявки, экономя ресурсы и предоставляя четкую причину отказа. Создание нового маршрута усложнило бы диаграмму и логику без необходимости, так как такие заявки не должны попадать в систему согласования вообще.

## Решение 2: Вынесение проверки в отдельный метод

**Формулировка:** Логика проверки допустимости вынесена в публичный метод `addUrgentPersonalCheck`.

**Альтернатива:** Оставить проверку только внутри `route()` и требовать от вызывающего кода обрабатывать исключение.

**Обоснование:** Публичный метод позволяет выполнять предварительную валидацию без накладных расходов на создание исключения (stack trace). Это соответствует принципу separation of concerns: валидация входных данных отделена от бизнес-логики маршрутизации. Caller может использовать этот метод в UI для блокировки недопустимых комбинаций до отправки запроса, улучшая UX.

## Ответы на контрольные вопросы

**Вопрос 1:** Какая проверка защищает программу от наиболее вероятной ошибки?
Проверка `risk == null` в начале метода `route()` класса `ApprovalRouter`. Она расположена первой среди защитных условий, так как `null` — наиболее частая ошибка при передаче enum из внешних систем или баз данных. Без этой проверки последующее сравнение `risk == RiskLevel.HIGH` выбросило бы `NullPointerException`, что менее информативно, чем явное сообщение о контракте метода.

**Вопрос 2:** Какой метод содержит ключевое бизнес-правило?
Метод `route()` в классе `ApprovalRouter` содержит всю бизнес-логику приоритета правил R1–R5. Он размещен здесь, потому что является единственной точкой принятия решения о маршруте. Декомпозиция на private-методы (`requiresSecurityReview` и др.) делает код читаемым, но центральная цепочка if-else-if остается в `route()`, обеспечивая строгий порядок проверок и стратегию fail-fast.

**Вопрос 3:** Как Activity-диаграмма отражает код?
Блок TODO A1 на диаграмме "Проверить правила R1-R5 по приоритету" соответствует цепочке if-else-if в методе `route()`. Каждый ромб на диаграмме (R1: personal?, R2: HIGH?) соответствует одному условию if в коде. Стрелки "да" ведут к возврату маршрута (return), стрелки "нет" — к следующей проверке. Для варианта 26 перед блоком R1 добавлен ромб "Urgent+Personal?", который при "да" ведет к блоку ошибки.

**Вопрос 4:** Какое изменение затронет минимальное количество классов?
Изменение значения константы `FINANCE_LIMIT` (например, с 500_000 на 250_000) затронет только класс `ApprovalRouter`. Константа объявлена как `public static final long`, и все ссылки на нее в методе `route()` используют это имя. Изменение не требует правки логики, тестов (кроме граничных значений) или диаграмм. Это демонстрирует принцип локализации изменений через именованные константы.

## Фрагмент кода для анализа

Рассмотрим фрагмент с нарушением приоритета:
```java
if (urgent) return FAST_TRACK;
if (containsPersonalData) return SECURITY_REVIEW;
```
Техническая ошибка: правило R4 (urgent) проверяется раньше R1 (personal). Для входа 10000;true;LOW;true код вернет FAST_TRACK, хотя по спецификации должен вернуть SECURITY_REVIEW. Причина: нарушен порядок приоритетов R1>R2>R3>R4>R5. Исправление: переместить проверку containsPersonalData перед urgent. Связь с правилами: приоритет обеспечивает корректное разрешение пересечений; fail-fast гарантирует, что первое сработавшее правило определяет результат.
