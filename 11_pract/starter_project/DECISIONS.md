## 2. Часть А. Изменённое правило

Правило: добавление обязательного поля (изменение формата записи, R2 и валидация).

Что было: запись содержала три поля `inn;name;email`.

Что стало: запись содержит четыре поля `inn;name;email;website`. Поле `website` обязательно, должно
начинаться с `http://` или `https://` и содержать домен. `ClientCsvParser` теперь ожидает 4 поля,
`ClientValidator` проверяет website, записи `ClientDraft` и `Client` получили поле `website`.

Почему: адрес сайта — отдельный инвариант данных клиента. Проверка находится в `ClientValidator` рядом с
остальными правилами полей, парсер отвечает только за синтаксис строки. Строка из трёх полей отклоняется
парсером с сообщением «ожидается 4 поля», пустой или некорректный адрес — валидатором.

## 3. Часть Б. Новый метод

Класс: `ClientValidator`

Метод: `addWebsiteDomain`

Сигнатура: `public String addWebsiteDomain(String url)`

Назначение: возвращает домен из URL (часть между схемой и первым `/`, `?`, `#` или `:`) или пустую
строку, если URL некорректен. Метод используется самим валидатором: если домен получить нельзя, поле
website считается ошибочным.

Код метода:

```java
public String addWebsiteDomain(String url) {
    if (url == null) return "";
    String rest;
    if (url.startsWith("https://")) rest = url.substring("https://".length());
    else if (url.startsWith("http://")) rest = url.substring("http://".length());
    else return "";
    int end = rest.length();
    for (int i = 0; i < rest.length(); i++) {
        char c = rest.charAt(i);
        if (c == '/' || c == '?' || c == '#' || c == ':') { end = i; break; }
    }
    String host = rest.substring(0, end);
    if (host.isEmpty() || host.indexOf(' ') >= 0) return "";
    return host;
}
```

## Решение 1. Ошибка строки локализуется внутри цикла

Формулировка: `try/catch` находится в методе `processLine`, который вызывается из цикла по строкам, а не
оборачивает весь цикл. Каждая ошибка записывается как `ImportError(lineNumber, message)`.

Альтернатива: один общий `catch` вокруг цикла.

Обоснование: общий catch остановил бы импорт на первой плохой строке и потерял бы корректные записи
после неё. Отдельный метод `processLine` также позволяет использовать ту же логику в data-driven режиме.

## Решение 2. Разделение разбора и проверки

Формулировка: `ClientCsvParser` проверяет только форму строки (число полей, пробелы), `ClientValidator`
возвращает список всех проблем полей, `ClientImporter` решает, что делать с записью.

Альтернатива: валидация внутри парсера с выбросом исключения на первой проблеме.

Обоснование: список проблем показывает администратору все ошибки строки сразу, а смена правила (например,
длина ИНН) затрагивает только `ClientValidator`.

## 4. Ответы на контрольные вопросы

### Вопрос 1
Наиболее вероятная ошибка входных данных — неверный формат ИНН, поэтому главная защита — проверка ИНН в
методе `ClientValidator.checkInn`, вызываемом из `validate`. Она требует, чтобы ИНН состоял только из цифр и
имел длину 10 или 12 символов (правило R3). Вероятность ошибки высока, потому что ИНН набирают вручную или
выгружают из разных систем: теряют цифру, добавляют пробел, подставляют букву. Проверка расположена в
валидаторе, а не в парсере, поэтому парсер остаётся простым, а все проблемы записи собираются в один список и
попадают в `ImportResult` с номером строки.

### Вопрос 2
Ключевое бизнес-правило — набор проверок полей записи клиента (R3 для ИНН, R4 для email и правило website
моего варианта) в классе `ClientValidator`, метод `validate`. Я разместил его именно там, потому что правила
предметной области должны быть отделены от чтения файла и от разбора строки. `ClientCsvParser` знает только про
формат CSV, `ClientImporter` — про порядок обработки и подсчёт результата. Если изменится требование, например
длина ИНН, правка коснётся одного класса. Кроме того, валидатор легко тестировать без файлов, передавая
`ClientDraft` напрямую.

### Вопрос 3
Блок «A1: Разобрать и проверить строку» на Activity-диаграмме соответствует двум вызовам в методе
`ClientImporter.processLine`: `parser.parse(line, lineNumber)` и `validator.validate(draft)`. Ромб «Строка
корректна?» — это проверка `problems.isEmpty()`, ветка «нет» ведёт к блоку «Записать ImportError», то есть к
`result.addError(new ImportError(lineNumber, ...))`, а ветка «да» — к проверке дубликата и сохранению
`repository.save(...)` с `result.addAccepted()`. Стрелки «back-edge» к чтению следующей строки отражают цикл
`while` в `importFile`, который не прерывается после ошибки (R6).

### Вопрос 4
Минимальное число классов затрагивает изменение правила длины ИНН, например вместо 10 или 12 цифр только
10. Меняется один метод `checkInn` в `ClientValidator`. Парсер не зависит от смысла полей, импортёр лишь
получает от валидатора список проблем, `ImportResult` и репозиторий вообще не знают об ИНН-правилах. Меняются
только ожидания в тестах и строки sample.csv, где ИНН имеет 12 цифр. Это следствие разделения ответственности:
каждое правило находится в одном месте и не размножено по классам.

## 5. Фрагмент кода для анализа

Фрагмент:

```java
try {
    for (String line : lines) importLine(line);
} catch (Exception e) {
    return; // первая плохая строка останавливает весь импорт
}
```

Проблема: общий `catch` вокруг всего цикла перехватывает исключение от любой строки и завершает метод,
поэтому все следующие строки, включая корректные, не обрабатываются. Это нарушает R6 (продолжение импорта
после ошибки) и R5: ошибка не записывается с номером строки, а `catch (Exception e)` ещё и скрывает
посторонние сбои, например ошибки программиста.

Исправление: перенести `try/catch` внутрь цикла и записывать ошибку строки:

```java
for (String line : lines) {
    lineNumber++;
    try {
        importLine(line);
    } catch (IllegalArgumentException e) {
        result.addError(new ImportError(lineNumber, e.getMessage()));
    }
}
```
