# DECISIONS.md – Практическая работа 12

## Вариант

Номер варианта: 26 mod 8 + 1 = 3. Изменяемый аспект — дополнительный агрегат, параметр 20.

Реализованное правило: `SalesAnalyticsService.commissionByManager(sales)` возвращает новый `Map<String, Double>`:
комиссия менеджера = 20 % от суммы его продаж. Процент задан единственной константой
`SalesAnalyticsService.COMMISSION_PERCENT = 20.0` и нигде больше не дублируется (в тестах используется константа).
Менеджер без продаж в результат не попадает, пустой список даёт пустой Map, нулевая сумма даёт комиссию 0.0.

## Решение 1. Единый Comparator с двумя полями и вся сортировка только через него

Формулировка: порядок «сумма по убыванию, затем id по возрастанию» задан один раз в константе
`BY_AMOUNT_DESC_THEN_ID` и используется в `topSales`, `maxSale` и `largeSales`.

Альтернатива: ручная сортировка или отдельный компаратор в каждом методе.

Обоснование: при равных суммах результат должен быть детерминированным (ничья S3/S5 всегда решается в пользу
S3), а изменение порядка сортировки меняется в одном месте. `maxSale` реализован как `min` по тому же
компаратору, поэтому он согласован с первой строкой `topSales` и возвращает `Optional`.

## Решение 2. Метод ничего не меняет: проверка аргументов, терминальные операции вместо forEach

Формулировка: каждый публичный метод проверяет `null`-список (`IllegalArgumentException`), а результат
собирается терминальными операциями (`toList`, `collect`, `min`, `average`), без изменения внешних коллекций
внутри stream.

Альтернатива: накапливать результат в внешнем `ArrayList` через `forEach(result::add)`.

Обоснование: stream с побочным эффектом ломается на параллельном выполнении и скрывает поток данных; тест с
`List.of(...)` (неизменяемый список) сразу ловит любую попытку модификации.

## Ответы на «собственные формулировки»

**Какая проверка защищает от наиболее вероятной ошибки входных данных и где она расположена.**
Наиболее вероятная ошибка — отсутствующий список или некорректная строка данных. Метод `requireSales` в
`SalesAnalyticsService` отсекает `null`-список во всех публичных методах, `topSales` дополнительно
отклоняет отрицательный `limit`, а `averageByRegion` — пустой регион. Ошибки формата файла (число полей,
сумма не число, отрицательная сумма, пустые поля, повторный id) ловит `SaleCsvLoader.parse` с номером строки.

**Какой метод или класс содержит ключевое бизнес-правило и почему.**
Ключевые правила находятся в `SalesAnalyticsService`: порядок сортировки (`BY_AMOUNT_DESC_THEN_ID`), порог
крупной сделки (`LARGE_DEAL_THRESHOLD`) и комиссия (`COMMISSION_PERCENT`). Я собрал их в сервисе, потому что
`Sale` — просто носитель данных, а загрузчик отвечает только за чтение. Пороги заданы константами в одном
классе, поэтому изменение правила не размножается по классам.

**Как Activity-диаграмма отражает участок кода.**
Блок «A1: Отфильтровать по условию метода» соответствует `.filter(s -> s.amount() >= min)` в `topSales`.
Следующий блок (сортировка/группировка) — `.sorted(BY_AMOUNT_DESC_THEN_ID)` или
`Collectors.groupingBy(Sale::manager, ...)`, блок терминальной операции — `.limit(limit).toList()`,
`.min(...)` или `.collect(...)`. Ромб «Результат найден?» отражает `Optional.empty()` или пустую
коллекцию при отсутствии подходящих продаж.

**Какое изменение требования затронет минимальное число классов.**
Изменение процента комиссии (например, с 20 на 25) затрагивает только константу `COMMISSION_PERCENT` в
`SalesAnalyticsService`. Тесты используют константу, поэтому меняются лишь ожидаемые числа в двух проверках.
`Sale`, `SaleCsvLoader` и диаграммы остаются прежними.

## Фрагмент для анализа

```java
List<Sale> result = new ArrayList<>();
sales.stream().filter(this::isLarge).forEach(result::add);
```

Ошибка: внутри stream изменяется внешняя коллекция `result` — это побочный эффект, нарушающий правило
работы («внутри stream запрещено модифицировать внешнюю ArrayList»). Такой код небезопасен при
`parallelStream`, смешивает императивный и функциональный стили и скрывает результат от читателя.

Исправление в проекте (`SalesAnalyticsService.largeSales`):

```java
return sales.stream().filter(this::isLarge).sorted(BY_AMOUNT_DESC_THEN_ID).toList();
```

## Сравнение цикла и stream

`averageByRegionImperative` (цикл с накоплением суммы и счётчика) требует двух переменных и проверки деления
на ноль, `averageByRegion` на stream выражает то же `filter → mapToDouble → average → orElse(0.0)` в одном
выражении. Тест `stream и цикл дают одинаковый результат` подтверждает эквивалентность.
