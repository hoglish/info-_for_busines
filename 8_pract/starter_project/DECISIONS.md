# DECISIONS.md

## Вариант

Номер варианта: 26

Часть А: R3 – submit блокируется, если у сотрудника уже есть активная командировка (статус SUBMITTED или APPROVED). Проверка реализована в методе create класса BusinessTripService. Обоснование: сотрудник не может иметь две активные командировки одновременно, это противоречит бизнес-правилам учёта рабочего времени и приводит к конфликтам при расчёте суточных и издании приказов.

Часть Б: addActiveTripsCount(BusinessTripService service) → int – возвращает количество активных командировок (SUBMITTED или APPROVED). Использует service.findAll() и цикл по всем заявкам с проверкой статуса. Применяется для мониторинга загрузки сотрудников и верификации корректности работы сервиса.

## Решение 1

Формулировка: проверка наличия активной командировки в методе create класса BusinessTripService. Перед созданием новой заявки выполняется цикл по всем существующим заявкам; если найдена заявка со статусом SUBMITTED или APPROVED, выбрасывается IllegalStateException с сообщением «У сотрудника уже есть активная командировка».

Альтернатива: реализовать проверку внутри метода submit() класса BusinessTrip, передавая в него ссылку на сервис или репозиторий. В этом случае заявка сначала создаётся в статусе DRAFT, а блокировка происходит при попытке перевода в SUBMITTED.

Обоснование: первый вариант предпочтительнее, так как блокирует создание заявки на более раннем этапе (fail-fast). Это экономит ресурсы системы и предоставляет пользователю понятную причину отказа до начала заполнения данных заявки. Размещение проверки в сервисном слое соответствует принципу разделения ответственности: BusinessTrip отвечает за управление своим состоянием, а BusinessTripService – за координацию и бизнес-правила, затрагивающие несколько заявок.

## Решение 2

Формулировка: метод addActiveTripsCount реализован как статический метод в SelfCheck, принимающий BusinessTripService параметром. Возвращает количество заявок со статусом SUBMITTED или APPROVED через цикл по service.findAll().

Альтернатива: добавить метод getActiveTripsCount() непосредственно в класс BusinessTripService как instance-метод.

Обоснование: для целей данной практической работы достаточно внешнего наблюдателя в SelfCheck. Добавление методов подсчёта в сам сервис нарушало бы принцип единственной ответственности (SRP), так как сервис должен заниматься только созданием и поиском заявок, а не метриками. Внешний статический метод позволяет проверять состояние системы, не изменяя контракт хранилища, и легко тестируется через unit-проверки.

## Ответы на контрольные вопросы

### Вопрос 1

Наиболее вероятной ошибкой входных данных в данной работе является нарушение инварианта дат: start > end (дата начала позже даты окончания). Эта проверка расположена в конструкторе класса BusinessTrip (правило R2) и выполняется первой среди всех инвариантов объекта. Ошибка наиболее вероятна, потому что даты часто вводятся вручную пользователем или приходят из внешних систем (календарь, форма заявки), где возможны опечатки, перепутанные поля или некорректный выбор диапазона. Ранняя проверка в конструкторе (fail-fast) предотвращает создание объекта в некорректном состоянии: если бы объект создавался с start > end, последующие методы (complete, расчёт длительности) работали бы с противоречивыми данными, что привело бы к логическим ошибкам в бизнес-процессе оформления командировки.

### Вопрос 2

Ключевое бизнес-правило – таблица допустимых переходов состояний (R3, R5, R7, R8) – содержится в пяти доменных методах класса BusinessTrip: submit, approve, reject, cancel, complete. Каждый метод проверяет текущий статус перед выполнением перехода и выбрасывает IllegalStateException при недопустимом состоянии. Размещение логики именно здесь обусловлено принципом инкапсуляции: объект BusinessTrip является единственным владельцем своего состояния (поле status private), поэтому только он может гарантировать корректность переходов. Если бы проверки находились в сервисном слое (BusinessTripService), это нарушило бы принцип единственной ответственности и привело бы к дублированию кода при каждом обращении к заявке из разных частей системы.

### Вопрос 3

Блок «Проверить допустимость перехода» на Activity-диаграмме соответствует цепочке проверок в каждом доменном методе класса BusinessTrip. Например, в методе submit() это условие if (status != TripStatus.DRAFT) throw new IllegalStateException(...). Ромб на диаграмме визуализирует условный оператор if: ветка «да» (статус корректен) ведёт к блоку изменения статуса, ветка «нет» – к блоку выброса исключения. Для варианта 26 добавлен дополнительный ромб «Активная командировка существует?» в методе create сервиса, который проверяет наличие заявок со статусом SUBMITTED или APPROVED перед созданием новой. Это отражает высший приоритет бизнес-правила: ограничение на количество активных командировок применяется до создания объекта.

### Вопрос 4

Изменение минимальной длины причины отклонения (правило R6) с 10 на 20 символов затронет только один метод – reject() в классе BusinessTrip. Константа порога длины может быть вынесена в private static final int MIN_REASON_LENGTH = 10, и изменение потребует правки только одной строки кода. Это демонстрирует принцип локализации изменений: правило валидации данных инкапсулировано внутри метода, отвечающего за переход в состояние REJECTED, и не распространяется на другие классы (BusinessTripService, SelfCheck, TripStatus). Даже если причина отклонения используется в отчётах или уведомлениях, изменение порога не потребует правки логики этих компонентов, так как они работают с уже валидированной строкой.

## Фрагмент кода для анализа

Рассмотрим фрагмент с нарушением инкапсуляции:
```java
public void setStatus(TripStatus status) { this.status = status; }
```

Техническая ошибка: открытый setter позволяет внешнему коду установить любой статус без проверки допустимости перехода. Пример атаки: вызов trip.setStatus(COMPLETED) из состояния DRAFT обходит все проверки R3/R5/R7/R8/R9 и переводит заявку в терминальное состояние нелегитимно. Исправление: удалить setter, изменять статус только через доменные методы (submit, approve, reject, cancel, complete), каждый из которых проверяет текущий статус перед переходом. Связь с правилом R10: поля status и rejectionReason объявлены private без setter именно для того, чтобы инварианты переходов гарантировались классом BusinessTrip, а не вызывающим кодом.
