# DECISIONS.md

## Индивидуальный вариант №26

### Часть А (корректировка архитектуры):
Добавлен класс `OrderRepository`, хранящий список всех созданных заказов (`List<Order>`). Метод `createOrder` в `OrderService` теперь не просто возвращает новый объект, но и автоматически сохраняет его в репозиторий. Это реализует паттерн Repository на минимальном уровне без использования фреймворков.

### Часть Б (новый метод):
Добавлен статический метод `addRepositoryCount(OrderRepository repo) → int`. Возвращает текущее количество заказов в репозитории через вызов `repo.findAll().size()`. Используется для верификации корректности сохранения заказов сервисным слоем.

## Решение 1: Автоматическое сохранение в конструкторе сервиса

**Формулировка:** Сохранение заказа в репозиторий происходит внутри метода `createOrder` сразу после создания объекта `Order`.a

**Альтернатива:** Вынести сохранение в отдельный метод `saveOrder` или делать это вручную в `SelfCheck` после каждого вызова `createOrder`.

**Обоснование:** Размещение сохранения внутри `createOrder` гарантирует, что ни один заказ не будет потерян («orphaned order»). Это соответствует принципу инкапсуляции бизнес-логики: создание заказа неразрывно связано с его регистрацией в системе. Caller не должен помнить о необходимости ручного сохранения — это снижает риск ошибок в клиентском коде.

## Решение 2: Статический вспомогательный метод для тестирования

**Формулировка:** Метод `addRepositoryCount` сделан статическим и вынесен в `SelfCheck` (или как утилитный метод), принимающим репозиторий параметром.

**Альтернатива:** Добавить метод `getCount()` непосредственно в класс `OrderRepository`.

**Обоснование:** Для целей данной практической работы достаточно внешнего наблюдателя. Добавление методов подсчета в сам репозиторий нарушало бы принцип единственной ответственности (SRP), так как репозиторий должен заниматься только хранением и поиском, а не метриками. Внешний метод позволяет проверять состояние системы, не изменяя контракт хранилища.

## Ответы на контрольные вопросы

**Вопрос 1.** Какая проверка защищает программу от наиболее вероятной ошибки входных данных?
Наиболее вероятной ошибкой является нарушение инварианта цены товара (`price <= 0`). Проверка расположена в конструкторе класса `Product`. Именно цена чаще всего приходит из внешних источников (CSV, API, ввод пользователя) в некорректном формате. Ранняя проверка в конструкторе (fail-fast) предотвращает создание «битых» объектов, которые могли бы привести к ошибкам при расчете итоговой суммы заказа или резервировании склада.

**Вопрос 2.** Какой метод содержит ключевое бизнес-правило и почему он размещен там?
Метод `addProduct` в классе `Order` содержит правило R7 (объединение повторов). Он размещен именно здесь, потому что `Order` является корнем агрегата и единственным владельцем списка позиций. Только заказ знает свой текущий состав и может принять решение: создать новую позицию или увеличить количество существующей. Размещение этой логики вне `Order` нарушило бы инкапсуляцию и привело бы к дублированию кода поиска по ID.

**Вопрос 3.** Как Activity-диаграмма отражает конкретный участок кода?
Блок «Товар уже есть в заказе?» на диаграмме соответствует циклу `for (OrderItem item : items)` в методе `addProduct`. Ветка «Да» ведет к блоку обновления количества, что реализовано вызовом `item.increase(quantity)`. Ветка «Нет» ведет к созданию новой позиции `items.add(...)`. Цикл на диаграмме (back-edge от «Есть еще товары?» к «Получить товар») отражает интерактивный режим или пакетную загрузку из CSV, где товары добавляются последовательно до исчерпания входных данных.

**Вопрос 4.** Какое изменение требования затронет минимальное количество классов?
Изменение максимального количества товара в позиции (R4) с 100 на 50 затронет только класс `OrderItem` (метод `setQuantity`). Поскольку проверка диапазона локализована в одном приватном методе, изменение константы не потребует правок в `Order`, `Product` или `OrderService`. Это демонстрирует преимущество инкапсуляции: правила валидации состояния объекта скрыты внутри него и не распространяются на другие компоненты системы.

## Фрагмент кода для анализа

Рассмотрим фрагмент с нарушением инкапсуляции:
```java
public List<OrderItem> getItems() { return items; }
```
Техническая ошибка: метод возвращает прямую ссылку на изменяемый внутренний список items. Причина: отсутствие защитного копирования при экспозиции коллекции. Исправление: использовать return List.copyOf(items); (R11). Последствия: внешний код может добавить/удалить позиции в обход addProduct, нарушив инварианты объединения повторов (R7) и проверки статуса (R8). Возврат неизменяемой копии гарантирует, что внутреннее состояние заказа контролируется только самим объектом Order.
